# Revues de propositions IA


## Revue : contournement proposé (Rosetta 2) face à l'échec de build `Grpc.Tools` sur Apple Silicon

* **Proposition et référence dans le dépôt** : lors de la mise en place du service gRPC (`BattleShip.API.csproj` et `BattleShip.App.csproj`), la commande "dotnet build" a échoué avec "Bad CPU type in executable" sur le protoc fourni par Grpc.Tools. L'IA a proposé d'installer Rosetta 2 "softwareupdate --install-rosetta --agree-to-license" pour l'exécuter sur ce Mac Apple Silicon (arm64).
* **Hypothèse à vérifier** : Rosetta 2 est-elle réellement nécessaire, ou existe-t-il un binaire protoc/grpc_csharp_plugin natif arm64 dans une version plus récente du package Grpc.Tools ?
* **Scénario, données ou commande** : comparaison de la version de Grpc.Tools réellement résolue par chaque projet livré par les versions 2.83.0 et 2.84.0.
* **Résultat attendu avant exécution** : si l'hypothèse « Rosetta indispensable » est vraie, les deux versions ne devraient proposer qu'un dossier macosx_x64.
* **Erreur que ce contrôle pourrait détecter** : une affirmation de l'IA non vérifiée qui aurait fait installer à l'utilisateur un composant système inutile.
* **Résultat réellement observé** : BattleShip.API résolvait Grpc.Tools en 2.83.0 (qui appelé indirectement par Grpc.AspNetCore), dont tools/ ne contient qu'un dossier macosx_x64 (binaire x86_64 donc pas arm64 qui est pour les apple silicon). BattleShip.App référençait explicitement 2.84.0, avce tools/ qui contient un dossier macosx_universal (binaire universel comprenant x64 et arm64). L'hypothèse était donc fausse.
* **Décision et justification** : proposition initiale (Rosetta 2) rejetée ; adaptée en épinglant explicitement Grpc.Tools en version 2.84.0 dans BattleShip.API.csproj, comme c'était déjà le cas côté BattleShip.App. Solution ciblée sur la cause réelle (version obsolète sans binaire arm64), sans modification système.
* **Preuves reproductibles et liens vers les commits** : `dotnet build` puis `dotnet test` sur l'ensemble de la solution après correction depuis la racine.
* **Après correction éventuelle : résultat avant / après** : avant : `dotnet build` échouait sur `back/BattleShip.API` avec `MSB6003: Bad CPU type in executable`. Après — `dotnet build` : 0 erreur sur les 4 projets de la solution ; `dotnet test` : 20/20 tests réussis, sans Rosetta 2 installée sur la machine
* **Limites et points non vérifiés** : cette vérification porte sur la chaîne de build à un instant donné ; elle ne garantit pas que le binaire macosx_universal restera disponible dans les futures versions de `Grpc.Tools`, ni qu'une mise à jour de `Grpc.AspNetCore` ne réintroduira pas une version plus ancienne en dépendance transitive.

## Revue : respect des principes SOLID dans le socle implémenté

* **Proposition et référence dans le dépôt** : l'ensemble du socle généré par l'IA.
* **Hypothèse à vérifier** : le code respecte-t-il raisonnablement les principes SOLID, ou l'IA a-t-elle produit du code plausible mais mal structuré (couplage fort, responsabilités mélangées) ?
* **Scénario, données ou commande** : relecture manuelle principe par principe.
* **Résultat attendu avant exécution** : si le principe d'inversion des dépendances (DIP) est respecté, le moteur de jeu (`Game`) devrait dépendre d'une abstraction pour la stratégie de l'ordinateur plutôt que d'une implémentation concrète, et cela devrait être visible dans la façon dont les tests substituent cette stratégie.
* **Erreur que ce contrôle pourrait détecter** : un couplage fort empêchant de faire évoluer une partie du code (ex. changer l'IA adverse) sans modifier le moteur de jeu, ou des composants aux responsabilités mélangées rendant le code difficile à faire évoluer et pour la sécurité.
* **Résultat réellement observé** : `Game` dépend de l'interface `IComputerStrategy`, pas de `RandomComputerStrategy` directement, qui substitue un `StubComputerStrategy` sans modifier `Game` (OCP/DIP/LSP respectés). `ShotRequestValidator` est consommé via `IValidator<ShotRequest>` injecté par Dependency Injection dans l'endpoint, pas instancié en dur (DIP respecté). Chaque classe du moteur (`Ship`, `Board`, `Game`) a une responsabilité distincte et cohérente (SingleResponsability respecté).
* **Décision et justification** : structure globale **acceptée** sans modification immédiate. Les deux points faibles sont des compromis assumés, `GameStore` : éviter une abstraction prématurée pour un unique consommateur ; `Home.razor` : taille encore raisonnable pour le périmètre actuel du socle plutôt que des défauts à corriger dans l'urgence. À réexaminer si `Home.razor` grossit sensiblement avec la suite.
* **Preuves reproductibles et liens vers les commits** : lecture directe de `IComputerStrategy.cs`, `Game.cs`, `GameStatsGrpcService.cs` et `Home.razor` ; comportement de substitution vérifié par l'exécution de `GameTests.cs` (20/20 tests réussis, y compris ceux utilisant `StubComputerStrategy`).
* **Après correction éventuelle : résultat avant / après** : aucune correction appliquée à ce stade — revue de constat, aucun défaut ne justifiant une correction immédiate.
* **Limites et points non vérifiés** : revue basée sur une lecture manuelle du code, pas sur un outil d'analyse statique dédié (ex. analyseur Roslyn) ; le couplage de `Home.razor` n'a pas été mesuré quantitativement (complexité cyclomatique, nombre de responsabilités) ; les principes ont été évalués sur le socle actuel, pas sur les extensions futures du backlog.

## Revue : ajout de `Grpc.Core.Testing` pour tester le service gRPC sans lancer de vrai serveur

* **Proposition et référence dans le dépôt** : pour tester `GameStatsGrpcService.GetStats` (jusque-là non testé du tout, 0% de couverture), l'IA a ajouté le paquet `Grpc.Core.Testing` (version 2.46.6) à `BattleShip.Tests.csproj` et écrit `GameStatsGrpcServiceTests.cs`, qui appelle le service directement avec un `ServerCallContext` fabriqué via `TestServerCallContext.Create(...)`.
* **Hypothèse à vérifier** : `Grpc.Core.Testing` dépend de `Grpc.Core`, l'ancienne implémentation gRPC basée sur une bibliothèque C native (`grpc_csharp_ext`) — pas celle qu'on utilise pour l'API (`Grpc.AspNetCore`, en pur .NET). Vu qu'on s'est déjà fait avoir une fois avec un paquet gRPC sans binaire natif arm64 (voir la revue Rosetta 2 plus haut), la question se pose direct : est-ce que ce nouveau paquet a le même problème sur ce Mac Apple Silicon ?
* **Scénario, données ou commande** : inspection du dossier `runtimes/` du paquet `Grpc.Core` 2.46.6 restauré dans `~/.nuget/packages`, et vérification de ce qui est réellement copié dans `back/BattleShip.Tests/bin/Debug/net10.0/runtimes/` après un `dotnet test` ; `uname -m` pour confirmer l'architecture de la machine.
* **Résultat attendu avant exécution** : si le risque est réel, soit les tests plantent avec une `DllNotFoundException` sur cette machine arm64, soit ils passent « par chance » à cause d'une émulation Rosetta déjà présente — ce qui masquerait un problème qui réapparaîtrait ailleurs (poste du binôme, machine du correcteur).
* **Erreur que ce contrôle pourrait détecter** : un test qui ne fonctionne que sur la machine où il a été écrit, à cause d'un binaire natif incompatible avec l'architecture d'une autre machine.
* **Résultat réellement observé** : le dossier `runtimes/` de `Grpc.Core` 2.46.6 ne contient que `osx-x64`, `linux-x64`, `linux-arm64`, `win-x86` et `win-x64` — pas de `osx-arm64` du tout, donc oui le même souci existe en théorie sur ce paquet. Mais les 3 tests passent quand même sans Rosetta 2 installée sur la machine (vérifié, elle n'est pas installée). En regardant d'un peu plus près ce que fait `TestServerCallContext.Create`, il ne construit qu'un objet managé (des délégués C# pour les callbacks comme `writeHeadersFunc`) : il ne passe jamais par le vrai runtime natif de `Grpc.Core`, qui ne sert qu'à faire circuler de vrais paquets réseau sur un vrai canal gRPC — chose qu'on ne fait pas ici puisqu'on appelle directement la méthode du service.
* **Décision et justification** : gardé tel quel, le risque flairé au départ ne se matérialise pas dans ce cas précis. Je note quand même le point pour la suite du projet : si un jour on ajoute un vrai test de bout en bout avec un canal gRPC réel (pas juste un contexte fabriqué), le manque de binaire `osx-arm64` redeviendrait un vrai blocage, comme pour `Grpc.Tools` à l'époque.
* **Preuves reproductibles et liens vers les commits** : `dotnet test back/BattleShip.Tests/BattleShip.Tests.csproj --filter "FullyQualifiedName~GameStatsGrpcServiceTests"` (3/3 réussis) ; contenu du dossier `~/.nuget/packages/grpc.core/2.46.6/runtimes` comparé à celui effectivement copié dans `bin/Debug/net10.0/runtimes`.
* **Après correction éventuelle : résultat avant / après** : aucune correction nécessaire, la proposition initiale tient la route une fois vérifiée.
* **Limites et points non vérifiés** : je n'ai pas de machine Apple Silicon sans Rosetta du tout sous la main pour re-tester à 100 % « à froid » (je me suis basé sur l'absence du dossier `osx-arm64` et sur le fait que les tests passent sans planter, pas sur une désinstallation réelle de Rosetta) ; le comportement sur Windows ou Linux n'a pas été vérifié, seulement macOS.

## Revue : sélecteur CSS `:has()` pour corriger une case à cocher qui « ne répondait pas »

* **Proposition et référence dans le dépôt** : Impossible de cocher « Mode Tempête » la case était en fait bien désactivée effectivement car on ne voulait pas le pouvoir avec le mode placer les pions manuellement (elle est incompatible avec le placement manuel des navires, déjà coché) mais rien ne le montrait visuellement, même curseur qu'une case normale. on a ajouté dans `Home.razor.css` une règle `.toggle-row:has(input:disabled)` pour griser la case et son texte quand c'est le cas.
* **Hypothèse à vérifier** : `:has()` est un sélecteur CSS relativement récent. Pour un projet démontré/noté sur un poste qu'on ne maîtrise pas forcément, est-ce un choix fiable ou est-ce qu'on risque que ça ne s'affiche pas du tout chez le correcteur ?
* **Scénario, données ou commande** : vérification du support navigateur de `:has()` (date d'arrivée dans les moteurs Chromium, WebKit), puis test visuel réel avant/après le correctif dans le navigateur utilisé pour les tests manuels de ce projet.
* **Résultat attendu avant exécution** : si `:has()` n'est pas supporté par un navigateur, la règle est simplement ignorée (pas de plantage) mais le bug resterait visible tel quel sur ce navigateur.
* **Erreur que ce contrôle pourrait détecter** : une correction qui a l'air de marcher dans l'environnement de test
* **Résultat réellement observé** : `:has()` est supporté depuis Chrome/Edge 105 (2022), Safari 15.4 (2022) et Firefox 121 (décembre 2023) il est donc disponible sur n'importe quel navigateur à jour. après le correctif, cocher « Placer mes navires moi-même » grise bien la case et le texte « Mode Tempête », avec un curseur « interdit » au survol ; décocher la rend normale à nouveau et elle redevient cliquable.
* **Décision et justification** : `:has()` gardé, le support est large et ne date plus d'hier. Par précaution quand même, la règle `input[type="checkbox"]:disabled` (opacité réduite, curseur interdit), qui elle est supportée depuis très longtemps partout, a été ajoutée en plus et indépendamment : même sans `:has()`, la case elle-même resterait visiblement grisée, seul le texte du label ne le serait pas.
* **Preuves reproductibles et liens vers les commits** : capture d'écran avant/après dans le navigateur de test ; règles ajoutées dans `Home.razor.css` (`.toggle-row:has(input:disabled)` et `.toggle-row input[type="checkbox"]:disabled`).
* **Après correction éventuelle : résultat avant / après** : avant — case « Mode Tempête » désactivée mais visuellement identique à une case active, clic sans aucun effet perceptible. Après — case et texte grisés, curseur « interdit », comportement clair.
* **Limites et points non vérifiés** : vérifié uniquement dans le navigateur intégré à l'outil de développement (moteur Chromium) ; pas re-testé avec Safari sur la machine (Un de nous deux est sur mac).
